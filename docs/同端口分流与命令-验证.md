> 环境：真实生产 Forge 服务端 1.20.1-47.3.0

## 1. 最终结果

```
✅ MC 原生 ping 正常 | 1.20.1 | {'text': 'A Minecraft Server'}     ← 分流未干扰 MC 流量
```

**同端口分流最难的地方不是"能分流"，而是"分流之后 MC 自己还能正常连"** —— 两项必须同时成立才算成功。

复现：

```bash
cd /workspace/packsync-testserver && ./run.sh nogui
# 另一个终端：
curl http://127.0.0.1:25565/packsync/v1/info     # 走 MC 端口，应返回 JSON
# 用任意 MC 客户端 ping 25565 也应正常
```

## 2. 实现方式的取舍

| | 常见做法 | PackSync |
|---|---|---|
| 分流依据 | 明文魔数 `AMMH` + 主机名 | **HTTP 方法 + `/packsync/` 路径前缀** |
| 之后做什么 | 原地升级 TLS，走自定义二进制协议 | 代理到本机内部的 HTTP 端口 |
| 客户端兼容性 | 必须用它的客户端 | **标准 HTTP 客户端（curl/浏览器/HttpURLConnection）直接可用** |

代价值得多：少一层自定义协议，换来的是"出问题时能用 curl 三秒定位"。

## 3. 攻坚过程中撞到的 5 个坑（全部已解决，留作维护警示）

### 坑 1：命令注册了但 Forge 说"Unknown or incomplete command"

- **现象**：`ServerStartedEvent` 正常工作，但 `/packsync host status` 报未识别命令。
- **根因**：`@Mod.EventBusSubscriber` 未显式指定 bus。虽然默认值是 `FORGE`，
  但显式写出来可以排除"订阅看似生效、命令却不注册"这类隐性问题。
- **修复**：`bus = Mod.EventBusSubscriber.Bus.FORGE`，并把注册日志提升到 INFO
  （`debug` 级在默认日志级别下看不到，等于没有）。

### 坑 2：mixin 配置"看起来完全没被加载"

- **现象**：日志里没有任何 mixin 处理痕迹，同端口分流不生效。
- **误判**：一度以为 Forge 不处理 jar-in-jar mod 的 mixin 配置。
- **诊断方法（值得复用）**：**故意把 mixins.json 的 `package` 改成一个不存在的包**。
  如果配置真的被加载，Forge 必然报 `Mixin prepare failed ... was not found`。
  结果立刻报错了 → **配置其实一直在正常加载，成功时本来就不打印日志**。
- **教训**：不要用"没有日志"推断"没有被执行"。

### 坑 3：注入被调用了，但代理连接一建立就失败

- **现象**：
  ```
  [sniff] 无法连接内部 HTTP 端口 25566
    -> java.lang.IllegalStateException: incompatible event loop type: io.netty.channel.epoll.EpollEventLoop
  ```
- **根因**：Linux 上 MC 用 **Epoll** event loop，而代理写死了 `NioSocketChannel`。
  Netty 要求出站 channel 与 event loop 类型一致。
- **修复**：按服务端连接的实际类型选择客户端 channel
  （`EpollSocketChannel` / `NioSocketChannel`）。

### 坑 4：`ByteToMessageDecoder` 里做管道移除 + 自建连接会互相打架

- **现象**：连接建立了，但一个字节都没回来。
- **根因**：`decode` 的约定是"消费多少、剩下多少自动传递"，
  而在里面同时做「移除自己 + 建第二条连接 + 转让已读字节」会与它的内部累积缓冲冲突。
- **修复**：改用 `ChannelInboundHandlerAdapter` 手动累积，字节归属与引用计数完全自控。

### 坑 5（最关键）：等满固定字节数再判断 → 与 MC 客户端互相等待

- **现象**：改了上面几处后分流通了，**但 MC 原生 ping 直接超时** ——
  说明分流器把正常游戏连接也卡住了。
- **根因**：原逻辑是"攒够 16 字节再判断"。而 MC 客户端发完握手包就**等响应**，
  我们则在**等够 16 字节**，双方互等形成死锁。
- **修复**：改成**渐进式前缀匹配** ——
  - 已能确定不是我们的流量 → **立即**交还 MC（MC 握手包的首字节是包长度 varint，
    不是 `G`/`P`/`H`/`O`，所以**第一个字节**就能排除）；
  - 只有"确实是某个模式的前缀"时才继续等（这种情况只可能是真的 HTTP 请求）。
- **验证**：修复后 MC ping 与 HTTP 分流**同时**正常。

> 这一条是本次最有价值的教训：**在别人的网络管线上做嗅探，
> 任何"等够 N 字节"的写法都可能与对端的交互节奏死锁。**

## 4. 命令清单

| 命令 | 权限 | 作用 |
|---|---|---|
| `/packsync`（别名 `/pks`） | 所有人 | 显示帮助 |
| `/packsync generate` | OP 3 | 重新生成清单并**即时生效**（不断开正在下载的玩家） |
| `/packsync host` / `host status` | OP 3 | 托管状态：端口、已发布文件数、活跃会话、清单规模、密钥目录 |
| `/packsync host start/stop/restart` | OP 3 | 托管控制 |
| `/packsync host fingerprint` | OP 3 | 服务器指纹（发给玩家核对） |
| `/packsync host keys` | OP 3 | 密钥目录位置 |
| `/packsync config reload` | OP 3 | 重载配置并重启托管（端口可能变化，所以整体重启最稳妥） |

所有命令**同步执行**且**保证不抛异常** —— 管理员敲一条命令不该把服务器搞崩。
