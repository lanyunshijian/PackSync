## 3. 端到端验证抓到的两个真实缺陷（已修复）

这两个问题**单元测试全都测不出来** —— 只有把服务端真跑起来、看真实清单内容才会暴露。

### 缺陷 1：默认配置会把服务端密钥同步给客户端（严重）

**现象**：默认 `syncedFiles` 含 `/config/**`，于是清单里出现了：

```
/config/fml.toml
/config/modsync/server-identity.dat     ← 别的 mod 的身份密钥！
/config/packsync-server.json            ← 本 mod 自己的配置
```

**危害**：每个客户端都会收到服务器上其它 mod 的密钥文件。

**修复（两层）**：
1. **默认值改为只含 `/mods/*.jar`** —— 与保守默认对齐，
   不再默认同步整个 `config/`（那里经常躺着密钥）
2. **兜底防线**：即使管理员显式配了 `/config/**`，
   `/modpack-keys/`、`/packsync/`、`/config/packsync-server.json` 也**永不进清单**
3. **敏感文件告警**：命中 `secret` / `identity` / `.key` / `token` 等特征的路径
   会被分发时打警告 —— 这类文件同步出去就是密钥泄露，而配置本身看不出异常，
   所以必须让风险**可见**

> 为什么不直接拦截所有"看起来像密钥"的文件：同名文件可能只是普通配置，
> 强行排除会破坏"同步配置"这个正当用法。选择告警而非拦截。

### 缺陷 2：本 mod 自己的 jar 混进了清单

**现象**：`/mods/packsync-1.0.0.jar` 出现在清单里。

**根因**：为了当"纯 locator"，外层 jar **不带 mods.toml**，
于是 `ModInspector` 认不出它的 modId，原先"按 modId 排除自身"的逻辑失效了。

**危害**：客户端会下载一份"把自己覆盖掉"的整合包。

**修复**：除 modId 外，**按 jar 内容特征识别自身**
（检查 jar 内是否含 `com/dsh/packsync/bootstrap/PackSyncModLocator.class`）。

### 修复后的清单（同一个服务端）

```
文件数: 3
   /config/client.toml          config        ← 来自 host/main，是要给客户端的
   /mods/modsync-1.0.0.jar      mod
   /resourcepacks/pack.zip      resourcepack
```

密钥、私有配置、自身 jar 全部消失。

## 4. 验证过程中踩到的环境坑（与 mod 本身无关，但会误导排查）

| 现象 | 真正原因 |
|---|---|
| `zip END header not found`，Forge 启动即崩 | 我往 `mods/` 放了**纯文本冒充的 .jar**。Forge 扫描 mods 目录时会打开每个文件，坏 zip 直接崩 |
| `No enum constant ...DependencySide.server` | 测试 jar 的 `mods.toml` 里 `side="server"` 写成了小写。Forge 的枚举是**大写** `SERVER` |
| `constructed 0 mods: [], but had 1 mods specified` | 测试 jar **没有 `@Mod` 类**。Forge 找到了 mod 声明却找不到可实例化的类 |

**教训**：验证用的假 mod 必须"长得像真 mod"——
合法 zip、合法 mods.toml、以及一个真正的 `@Mod` 类。否则会浪费大量时间在环境问题上。

另外：**PackSync 与 ModSync 的默认端口会冲突**（两者都用 `MC端口 + 1`）。
同时装这两个 mod 时需要给其中一个配置 `reconcilePort`。
