## 2. 为什么必须用生产服务端验证（dev 环境会给出错误结论）

| 环境 | `IModLocator` | `@Mod` 入口 |
|---|---|---|
| dev（`./gradlew runServer`） | **不被调用** | 正常加载 |
| 生产（真实服务端 `mods/`） | 被调用 | 需额外机制才能加载 |

dev 环境把 mod 作为 classpath 的一部分加载，不走 `mods/` 目录扫描，
因此 locator 根本不会触发。**只看 dev 环境会得出"locator 不工作"的错误结论**，
反之若只看 dev 的 `@Mod` 日志又会误以为一切正常。

## 3. 攻坚过程中撞到的 5 个坑（都已解决，留作后续维护的警示）

### 坑 1：声明了 IModLocator 的 jar 不再被当作普通 mod 加载

- **现象**：只注册 `services/IModLocator` 时，生产日志里**完全没有**该 mod 的加载痕迹，
  `mods.toml` 不生效，`@Mod` 类永不实例化；服务端却能正常启动（静默失效）。
- **原因**：Forge 把提供 locator 的 jar 视为"加载器提供者"，从常规 mod 发现中排除。
- **解法**：需要第二个 SPI（`IDependencyLocator`）显式把自己/内层装载为 mod。

### 坑 2：locator 阶段拿不到自身 jar 路径

- **现象**：`getProtectionDomain().getCodeSource().getLocation()` 返回 **`/`**（不是 jar 路径）。
- **后果**：拿它去 `createMod` 会直接崩：
  `java.lang.module.ResolutionException: Module forge reads more than one module named packsync`
- **解法**：**按内容扫描 `mods/` 目录定位自身** —— 打开每个 jar 找内含本类字节码的那个。
  不依赖类加载器给出路径，稳定可靠。

### 坑 3：同一个 jar 不能既是 locator 模块又是 mod 模块

- **现象**：`Module forge reads more than one module named packsync`
- **解法**：**两层 jar + 两个不同 modId**（这是通行的结构）：
  - 外层 `packsync-1.0.0.jar`（模块 `packsync`）：只有 locator + 平台无关核心，**不带 mods.toml**
  - 内层 `packsync-mod.jar`（模块 `packsync_mod`）：`@Mod` + 游戏内代码，由 locator 装载

### 坑 4：外层 jar 带 mods.toml 会报"缺元数据"

- **现象**：外层保留 `mods.toml`（modId=packsync）时报
  `mods.toml missing metadata for modid packsync`。
- **原因**：外层声明了 modId，却因提供 locator 而不会被注册为 mod，两边对不上。
- **解法**：**外层不提供 mods.toml**，只当 locator 容器。实测外层单独运行完全正常。

### 坑 5：`@Mod` 注解的值必须与 mods.toml 的 modId 完全一致

- **现象**：`mods.toml missing metadata for modid packsync`
  —— 但报的是 `packsync`，而 mods.toml 里明明写的是 `packsync_mod`，
  且 TOML 语法经 `tomllib` 校验完全合法、`[[mods]]` 数组长度正确。
- **根因**：`@Mod(PackSyncCore.MOD_ID)` 的值是 `packsync`，与内层 mods.toml 的
  `packsync_mod` 不一致。Forge 用注解值去 mods.toml 找元数据，找不到就报这个错。
- **解法**：新增 `PackSyncCore.MOD_ID_INNER = "packsync_mod"`，
  并确保**三者一致**：`@Mod` 值 == 内层 mods.toml 的 modId == `MOD_ID_INNER`。
- **警示**：这个错误信息**完全不会提示"注解写错了"**，且报的名字让人以为是外层问题，
  排查成本极高。已在代码注释中显式记录这条约束。

## 4. 副产品：内层 jar 需要 pack.mcmeta

内层被装载后，MC 会把它当资源包/数据包扫描，缺 `pack.mcmeta` 会报：

```
Missing metadata in pack mod:packsync_mod
Missing data pack mod:packsync_mod
```

不影响启动，但会刷警告。补齐内层 `pack.mcmeta` 后消失（已修复）。

## 5. 复现方式

```bash
# 1) 构建
cd /workspace/packsync
JAVA_HOME=/workspace/mc-mod-dev/toolchain/jdk-17 \
GRADLE_USER_HOME=/workspace/.gradle-home \
./gradlew build --no-daemon

# 2) 放入生产服务端
cp build/libs/packsync-1.0.0.jar /workspace/packsync-testserver/mods/

# 3) 启动（首次会生成世界，约 30 秒）
cd /workspace/packsync-testserver
JAVA_HOME=/workspace/mc-mod-dev/toolchain/jdk-17 ./run.sh nogui

# 4) 检查
grep -i packsync logs/latest.log
```

服务端安装方式（一次性）：Forge installer `--installServer`，见 `/workspace/packsync-testserver/`。
